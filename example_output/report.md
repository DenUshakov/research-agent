# Детальний порівняльний аналіз: Docker Swarm, Kubernetes та Nomad

Оркестрація контейнерів та системних навантажень — один із ключових елементів сучасної Cloud Native інфраструктури. Вибір правильного оркестратора залежить від вимог до масштабу, складності, типів завантажень та ресурсів команди.

Нижче наведено детальний порівняльний аналіз трьох популярних рішень: **Docker Swarm**, **Kubernetes (K8s)** та **HashiCorp Nomad**.

---

## 1. Загальний огляд та філософія

| Інструмент | Розробник / Екосистема | Філософія та підхід |
| :--- | :--- | :--- |
| **Docker Swarm** | Docker Inc. / Moby Project | **Вбудована простота**. Оркестратор є безпосередньо частиною Docker Engine. Націлений на мінімальний поріг входження та використання існуючого синтаксису `docker-compose`. |
| **Kubernetes** | CNCF (початково Google) | **Всеосяжна платформа ("All-in-One Framework")**. Декларативна модель з багатьма абстракціями, призначена для побудови складних, стійких та розширюваних хмарних систем. |
| **Nomad** | HashiCorp | **Unix-філософія ("Do one thing well")**. Планувальник задач (Workload Scheduler), який займається лише розкладом і запусків процесів, делегуючи мережу та секрети іншим спеціалізованим інструментам (Consul, Vault). |

---

## 2. Архітектура та складність

### **Docker Swarm**
* **Архітектура**: Кластер складається з двох типів вузлів — *Manager nodes* (керують станом кластера через протокол консенсусу Raft) та *Worker nodes* (виконують завдання/контейнери).
* **Складність**: Найнижча. Кластер ініціалізується однією командою: `docker swarm init`.
* **Залежності**: Не потребує сторонніх баз даних чи зовнішніх сервісів — все вбудовано в Docker Daemon.

### **Kubernetes**
* **Архітектура**: Складається з Control Plane (`kube-apiserver`, `etcd`, `kube-scheduler`, `kube-controller-manager`) та Worker Nodes (`kubelet`, `kube-proxy`, Container Runtime — containerd/CRI-O).
* **Складність**: Дуже висока. Вимагає глибокого розуміння багатьох об'єктів (Pods, Deployments, StatefulSets, Services, Ingress, PV/PVC, NetworkPolicies, RBAC).
* **Залежності**: Потребує `etcd` для збереження стану, CNI-плагіна (Flannel, Calico, Cilium), Ingress-контролера тощо.

### **Nomad**
* **Архітектура**: Одиничний бінарний файл (single binary), який може працювати як у режимі `server`, так і в режимі `client`. Використовує Raft для консенсусу між серверами та Serf для Service Discovery всередині кластера Nomad.
* **Складність**: Низька / Середня. Чітка та проста ієрархія: **Job** $\rightarrow$ **Task Group** $\rightarrow$ **Task**.
* **Залежності**: Не має обов'язкових зовнішніх залежностей для базового запуску, але для повноцінного Service Discovery та мережі інтегрується з **HashiCorp Consul**, а для управління секретами — з **HashiCorp Vault**.

---

## 3. Типи робочих навантажень (Workload Types)

* **Docker Swarm**: Підтримує **виключно Docker-контейнери**.
* **Kubernetes**: Орієнтований на контейнери (CRI: containerd, CRI-O). Для запуску віртуальних машин потрібні додаткові розширення (наприклад, KubeVirt).
* **Nomad**: **Універсальний оркестратор**. Завдяки концепції **Task Drivers** підтримує:
  * Docker та Podman контейнери
  * Нативні бінарні файли (Raw Exec / Exec)
  * Java-застосунки (`.jar`)
  * Віртуальні машини (QEMU/KVM)
  * MicroVMs (Firecracker)

---

## 4. Масштабованість, ресурсоємність та продуктивність

* **Docker Swarm**:
  * Вкрай низьке споживання ресурсів самим оркестратором.
  * Добре працює на сотнях вузлів, але при масштабуванні до тисяч вузлів чи частому переплануванні задач можуть виникати проблеми з продуктивністю Raft та overlay-мережі.

* **Kubernetes**:
  * Control Plane вимагає значних ресурсів (ОЗП/CPU) для `etcd` та API-сервера.
  * Офіційно підтримує кластери до 5 000 вузлів та 300 000 контейнерів.
  * Масштабування вимагає точної настройки системних параметрів та ресурсних лімітів.

* **Nomad**:
  * Дуже легковажний control plane.
  * Демонструє високу швидкість планування (доведено випробуванням *Million Container Challenge* — запуск 2 мільйонів контейнерів на 10,000 вузлах за 22 хвилини).
  * Споживає до 40–50% менше ресурсів на службові потреби у порівнянні з Kubernetes.

## 5. Мережа, Service Discovery та Зберігання

| Критерій | Docker Swarm | Kubernetes | Nomad |
| :--- | :--- | :--- | :--- |
| **Service Discovery** | Вбудований DNS та Ingress Routing Mesh (VIP) | Вбудований Kube-DNS / CoreDNS + ClusterIP | Через **HashiCorp Consul** (або нативний базований на Consul SD) |
| **Networking / CNI** | Вбудовані Overlay-мережі (VXLAN) | CNI плагіни (Calico, Cilium, Flannel, Weave) | CNI / Nomad Native / Consul Connect (Service Mesh) |
| **Управління секретами** | Docker Secrets (шифрування в Raft log) | Kubernetes Secrets (за замовчуванням base64 в etcd, вимагає KMS) | **HashiCorp Vault** (золотий стандарт індустрії) |
| **Зберігання (Storage)** | Docker Volume Plugins (local, NFS, third-party) | CSI (Container Storage Interface) — PV, PVC, StorageClasses | CSI (Container Storage Interface) + Host Volumes |

## 6. Екосистема, інструментарій та ліцензування

* **Kubernetes**: 
  * **Екосистема**: Найбільша в індустрії під егідою CNCF. Наявні тисячі інструментів (Helm, ArgoCD, Flux, Prometheus, Istio, Cert-Manager).
  * **Ліцензія**: Apache 2.0 (Open Source).
  * **Cloud Managed**: Усі великі хмарні провайдери пропонують керовані сервіси (AWS EKS, GCP GKE, Azure AKS).

* **Docker Swarm**:
  * **Екосистема**: Обмежена. Розвиток сповільнився після переорієнтації Docker Inc. на Docker Desktop та enterprise-рішення.
  * **Ліцензія**: Apache 2.0 (у складі Moby/Docker Engine).
  * **Cloud Managed**: Майже відсутній у хмарних провайдерів як керована послуга.

* **Nomad**:
  * **Екосистема**: Тісно інтегрована у стек HashiCorp (Terraform, Consul, Vault, Packer).
  * **Ліцензія**: З серпня 2023 року HashiCorp змінила ліцензію з MPL 2.0 на **BSL 1.1 (Business Source License)**, що накладає обмеження на комерційне використання компаніями, які надають конкурентні хмарні сервіси.
  * **Cloud Managed**: Зазвичай розгортається самостійно або в HashiCorp Cloud Platform (HCP).

## 7. Зведена порівняльна таблиця

| Характеристика | Docker Swarm | Kubernetes (K8s) | HashiCorp Nomad |
| :--- | :--- | :--- | :--- |
| **Поріг входження** | Дуже низький | Дуже високий | Низький / Середній |
| **Формат конфігурації** | YAML (`docker-compose.yml`) | YAML / JSON | HCL (HashiCorp Language) / JSON |
| **Формат навантаження** | Тільки Docker | Контейнери (CRI) | Контейнери, Binary, Java, QEMU/VM |
| **Розширюваність** | Низька | Висока (CRD, Operators) | Середня (Plugins, Custom Drivers) |
| **Автомасштабування** | Обмежене (потрібні сторонні скрипти) | Нативне (HPA, VPA, Cluster Autoscaler) | Через Nomad Autoscaler |
| **RBAC / Безпека** | Базове (в Docker Enterprise) | Повноцінний нативний RBAC | Повноцінний ACL & Token system |
| **Оверхед на ресурси** | Мінімальний (~50-100 MB RAM) | Значний (від 1-2 GB RAM на вузол) | Низький (~100-200 MB RAM) |

## 8. Плюси та мінуси кожного інструменту

### **Docker Swarm**
👍 **Плюси:**
* Готовий до роботи "з коробки" у будь-якій системі з встановленим Docker.
* Мінімальні вимоги до знань та інфраструктурних ресурсів.
* Простий синтаксис файлів конфігурації.

👎 **Мінуси:**
* Повільний розвиток та відсутність нових функцій.
* Обмежені можливості розгортання складних топологій та мережевих політик.
* Відсутність вбудованого складного автомасштабування та CRD.

---

### **Kubernetes**
👍 **Плюси:**
* Де-факто стандарт індустрії з величезною спільнотою та ринком фахівців.
* Максимальна гнучкість, наявність інструментів GitOps (ArgoCD), сервіс-мешів та операторів.
* Наявність готових керованих сервісів у будь-якому хмаровому провайдері (EKS, GKE, AKS).

👎 **Мінуси:**
* Надзвичайно висока складність адміністрування та крива навчання.
* Високе споживання системних ресурсів на функціонування Control Plane.
* "Overengineering" для невеликих проєктів чи команд.

---

### **HashiCorp Nomad**
👍 **Плюси:**
* Здатність оркеструвати не лише контейнери, а й бінарники, скрипти та віртуальні машини.
* Архітектурна простота (єдиний бінарник, низькі вимоги до ресурсів).
* Фантастична швидкість та продуктивність масштабування.
* Відмінна інтеграція з Consul та Vault.

👎 **Мінуси:**
* Зміна ліцензії на BSL 1.1 може створювати юридичні ризики для певних видів бізнесу.
* Менша спільнота у порівнянні з K8s, менше готових графіків/чартів (немає прямого аналога Helm Hub).
* Вимагає розгортання додаткових продуктів HashiCorp для повноцінного функціонування (Consul/Vault).

## 9. Підсумкові рекомендації з вибору (Use Cases)

1. **Обирайте Docker Swarm, якщо:**
   * У вас невелика команда або один DevOps-інженер.
   * Інфраструктура складається з 2–15 серверів і не планується вибухове зростання.
   * Ви вже використовуєте `docker-compose` і хочете отримати базову відмовостійкість без витрат часу на вивчення складної системи.

2. **Обирайте Kubernetes, якщо:**
   * Ви будуєте велику мікросервісну архітектуру у великій компанії або масштабованому стартапі.
   * Вам потрібні інструменти GitOps, складні політики безпеки (RBAC, Network Policies), Service Mesh та багата екосистема CNCF.
   * Ви плануєте використовувати керований хмарний кластер (EKS/GKE/AKS), делегувавши обслуговування Control Plane провайдеру.

3. **Обирайте Nomad, якщо:**
   * У вас є змішані (hybrid) робочі навантаження: застарілі моноліти (legacy binaries), Java-застосунки, VM разом із Docker-контейнерами.
   * Вам потрібна висока продуктивність та низьке споживання ресурсів (Edge computing, IoT, High-Performance Computing).
   * Ви вже активно використовуєте інструменти HashiCorp (Terraform, Consul, Vault) і шукаєте простий в операційному обслуговуванні оркестратор.
