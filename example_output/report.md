# Порівняльний аналіз архітектур API: REST проти GraphQL

## Вступ

При розробці сучасних веб- та мобільних додатків вибір архітектури взаємодії між клієнтом і сервером (API) є одним із ключових архітектурних рішень. Найбільш популярними підходами на сьогодні є **REST (Representational State Transfer)** — перевірений часом стандарт, та **GraphQL** — гнучка мова запитів, створена компанією Meta (Facebook).

Цей звіт надає детальний порівняльний аналіз обох підходів за основними технічними критеріями, їх перевагами, недоліками та практичними кейсами використання.

---

## 1. Основні концепції

### REST (Representational State Transfer)
REST — це **архітектурний стиль**, що базується на ресурсах. У REST кожна сутність (користувач, товар, замовлення) є ресурсом і має власний унікальний URI (Uniform Resource Identifier). Взаємодія з ресурсами відбувається через стандартні HTTP-методи:
* `GET` — отримання ресурсу
* `POST` — створення нового ресурсу
* `PUT` / `PATCH` — повне або часткове оновлення
* `DELETE` — видалення ресурсу

### GraphQL
GraphQL — це **мова запитів для API** (Query Language) та середовище виконання (runtime) для їх обробки. GraphQL не прив'язаний до типів ресурсів або URL. Замість кількох ендпоінтів використовується **один єдиний ендпоінт** (зазвичай `POST /graphql`), через який клієнт надсилає запит із чітким описом того, які саме дані та в якій формі йому потрібні.

## 2. Ключові технічні відмінності

### 2.1. Отримання даних: Over-fetching та Under-fetching

* **REST:**
  * **Over-fetching (Надмірне отримання):** Сервер повертає фіксовану структуру об'єкта. Якщо клієнту потрібне лише ім'я користувача, REST все одно поверне весь об'єкт (з адресою, телефоном, датою реєстрації тощо), що даремно витрачає мережевий трафік.
  * **Under-fetching (Недостатнє отримання):** Для відображення однієї сторінки (наприклад, профілю з останніми замовленнями) клієнту доводиться робити декілька послідовних запитів: `GET /users/1`, потім `GET /users/1/orders`. Це створює проблему "Waterfall requests".

* **GraphQL:**
  * **Точність даних:** Клієнт формує запит із зазначенням лише необхідних полів. Over-fetching повністю відсутній.
  * **Запит за один підхід:** Клієнт може отримати користувача, його замовлення та товари в них у межах **одного запиту**, описавши вкладену структуру.

### 2.2. Схема та Типізація

* **REST:**
  * Не вимагає строгої схеми за замовчуванням.
  * Контракти між фронтендом та бекендом часто описуються зовнішніми інструментами, такими як **OpenAPI / Swagger**. Без них існує ризик розсинхронізації типів.
* **GraphQL:**
  * Повністю побудований на **строго типізованій схемі (Schema Definition Language — SDL)**.
  * Схема слугує єдиним джерелом правди (Single Source of Truth) та дає автодоповнення, валідацію запитів "з коробки" та автоматичну генерацію типів для TypeScript.

### 2.3. Кешування

* **REST:**
  * **Нативне кешування HTTP:** Використовує стандартні HTTP-механізми (`Cache-Control`, `ETag`, `Last-Modified`, коди `304 Not Modified`).
  * Легко кешується на рівні браузера, CDN (Cloudflare, Fastly) та проксі-серверів за URL ресурсу.
* **GraphQL:**
  * Всі запити йдуть на один ендпоінт (зазвичай HTTP `POST`), тому стандартні HTTP-кеші та CDN не можуть автоматично кешувати відповіді за URL.
  * Кешування реалізується складно — або на рівні клієнтських бібліотек (нормалізований кеш в Apollo Client / Relay), або через складні серверні техніки (Persisted Queries, GraphQL Edge Caching).

### 2.4. Обробка помилок та статуси HTTP

* **REST:**
  * Використовує стандартні коди відповідей HTTP (`200 OK`, `201 Created`, `400 Bad Request`, `401 Unauthorized`, `404 Not Found`, `500 Server Error`).
  * Стан відповіді легко аналізувати на мережевому рівні.
* **GraphQL:**
  * Зазвичай **завжди повертає HTTP статус `200 OK`**, навіть якщо виникла помилка під час виконання запиту.
  * Помилки повертаються всередині JSON-структури у масиві `errors`. При цьому поле `data` може містити частково виконані дані (Partial Success).

### 2.5. Продуктивність та складність бекенду

* **REST:**
  * Проста обробка на бекенді. Легко налаштовувати обмеження частоти запитів (Rate Limiting) за окремими ендпоінтами.
* **GraphQL:**
  * **Проблема N+1 query:** При виконанні розв'язувачів (resolvers) для вкладених об'єктів сервер може робити сотні зайвих запитів до бази даних, якщо не використовувати спеціальні інструменти пакетної обробки (наприклад, `DataLoader`).
  * **Складність запитів:** Клієнт може надіслати надто глибокий або важкий запит, що здатне перевантажити сервер. Необхідно впроваджувати аналіз складності запиту (Query Cost/Depth Analysis).

### 2.6. Версіонування та еволюція

* **REST:**
  * Зміни API зазвичай вимагають версіонування у шляху URL (`/api/v1/users` -> `/api/v2/users`) або через HTTP-заголовки. Це призводить до необхідності підтримувати кілька версій API одночасно.
* **GraphQL:**
  * Працює за концепцією **безверсійного API (Continuous Evolution)**. Нові поля просто додаються до схеми, а застарілі відмічаються директивою `@deprecated`. Клієнти, які не запитують нові поля, продовжують працювати без змін.

## 3. Зведена порівняльна таблиця

| Критерій | REST API | GraphQL API |
| :--- | :--- | :--- |
| **Парадигма** | Архітектурний стиль (Resource-based) | Мова запитів та runtime (Query-based) |
| **Ендпоінти** | Множинні ендпоінти (`/users`, `/posts`) | Один ендпоінт (`/graphql`) |
| **Формат запиту** | Визначається HTTP-методом та URL | Описується мовою GraphQL (Query/Mutation) |
| **Отримання даних** | Можливий Over-fetching та Under-fetching | Клієнт запитує тільки необхідні поля |
| **Кешування** | Просте, нативне на рівні HTTP / CDN | Складне, реалізується на клієнті або через спеціальні проксі |
| **Типізація** | Опціональна (OpenAPI / Swagger) | Обов'язкова та строга (SDL) |
| **Обробка помилок** | Стандартні коди HTTP (404, 500 тощо) | HTTP 200 + масив `errors` у тілі JSON |
| **Версіонування** | Версіонування шляху (v1, v2) | Безверсійне, через депрекацію полів `@deprecated` |
| **Підтримка Real-time** | Через WebSockets, SSE або Polling | Нативні GraphQL Subscriptions (WebSocket/SSE) |
| **Складність бекенду** | Низька / Середня | Середня / Висока (потрібні DataLoader, Depth Limiting) |

## 4. Переваги та недоліки

### REST API

#### Переваги:
* **Простота та зрозумілість:** Стандарт індустрії з величезною екосистемою.
* **Відмінне кешування:** Проста інтеграція з CDN та браузерними кешами.
* **Передбачуваність навантаження:** Бекенд чітко знає, яку роботу виконуватиме кожен ендпоінт.
* **Легкість контролю доступу та Rate Limiting:** Просто обмежувати доступ до окремих маршрутів.

#### Недоліки:
* Надмірне або недостатнє отримання даних (Over/Under-fetching).
* Необхідність багатьох мережевих запитів для складних UI.
* Ризик розсинхронізації документації та реального API.

---

### GraphQL API

#### Переваги:
* **Максимальна гнучкість для клієнта:** Фронтенд отримує точно ті дані, які потрібні для конкретного компонента.
* **Один запит замість багатьох:** Зменшує кількість мережевих затримок (особливо актуально для мобільних мереж).
* **Строга типізація та автоматична документація:** Інструменти на кшталт GraphiQL / Apollo Studio згладжують процес розробки.
* **Швидка ітерація UI:** Фронтенд-розробники можуть змінювати UI без переписання бекенд-ендпоінтів.

#### Недоліки:
* **Складність на боці сервера:** Необхідність вирішення проблеми N+1, захисту від надто глибоких запитів.
* **Складність кешування:** Відсутність нативного HTTP-кешування.
* **Оверхед для простих задач:** Для простих CRUD-додатків GraphQL додає зайву складність.

## 5. Практичні рекомендації: Що обрати?

### Обирайте **REST API**, якщо:
1. Ваша система орієнтована на **стандартні CRUD-операції** з відносно простою структурою даних.
2. Проект активно використовує **CDN-кешування** (наприклад, контентні сайти, медиа-платформи, файлові сховища).
3. Ви розробляєте **відкрите публічне API** для зовнішніх розробників, де важлива простота інтеграції без вивчення додаткових інструментів.
4. У вашої команди немає досвіду роботи з GraphQL і проект має жорсткі дедлайни.

### Обирайте **GraphQL API**, якщо:
1. Ви будуєте **складний веб- або мобільний додаток** з багатьма зв'язаними сутностями (соціальні мережі, e-commerce, таск-менеджери, дашборди).
2. Важливо мінімізувати мережевий трафік для **мобільних пристроїв** із повільним з'єднанням.
3. У вас багато різних клієнтських платформ (iOS, Android, Web, SmartTV), кожна з яких вимагає свій набір полів.
4. Ви використовуєте **мікросервісну архітектуру** і хочете об'єднати дані з багатьох мікросервісів через єдину точку входу (GraphQL Gateway / Federation).

---

## Висновок

REST та GraphQL не є конкурентами, що виключають один одного — це два різні інструменти для вирішення різних задач. REST залишається надійним та простим вибором для стандартних сервісів із сильними вимогами до кешування. GraphQL виступає потужним рішенням для динамічних додатків із багатим UI, де гнучкість отримання даних виправдовує додаткову складність на бекенді. У багатьох сучасних архітектурах вони навіть успішно співіснують.
